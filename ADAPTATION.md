# ADAPTATION.md — перенос шаблона на нового клиента

Бриф до начала работы. Пароли и серверные ключи в бриф не пишутся.
Ниже — чек-лист и то, где это живёт в коде.

---

## 0. Что нужно от клиента

- Название компании, город, телефон, почта, сайт (если есть).
- Территория выезда (город / район / за город).
- Контакт владельца и кто будет пользоваться кабинетом.
- Прайс: категории, услуги, варианты, единицы измерения (`шт`, `м²`, `м.п.`),
  цены за единицу, min/max/step, опции и их привязка к вариантам.
- Минимальный заказ, правило округления, доплата за выезд за город.
- Как оцениваются спорные загрязнения и «Другое».
- Фото выполненных работ для блока «Наши работы» (по желанию, 3–5 штук; можно
  парами «до/после» с одного ракурса).
- Telegram-бот для уведомлений: токен, username, секрет webhook (если нужны
  уведомления о заявках; webhook регистрируется при подключении).
- Цвет, логотип, тексты компании (если нет — берём нейтральные из шаблона).
- Домен, хостинг, кто оплачивает продление.
- Согласованный объём работ.

## 1. Создать отдельный экземпляр

- [ ] Отдельный репозиторий или отдельная ветка — не общая с другим клиентом.
- [ ] Отдельная база данных. Никаких общих таблиц, заявок и фото.
- [ ] Отдельные серверные секреты: `DATABASE_URL`, `AUTH_SECRET`, доступ к хранилищу фото.
- [ ] Отдельный аккаунт хостинга на отдельную почту, которую можно передать владельцу.
- [ ] Домен клиента, HTTPS.

Данные другого клиента не копируются ни на каком шаге.

Команды:

```bash
npm ci
npm run db:migrate      # применить drizzle/ к базе клиента
npm run db:seed         # компания, тарифы, владелец из ADMIN_EMAIL/ADMIN_PASSWORD
```

Сид идемпотентен: повторный запуск не перезаписывает цены, изменённые в кабинете.

## 2. Конфиг компании

Файл `config/company.ts` (`src/config/company.ts`) — **только значения для первого сида**.
После установки источник правды — таблица `company`, её правит владелец в кабинете
«Компания». Правка конфига на работающем сайте ничего не изменит без повторного сида
в пустую базу.

- [ ] название, город, телефон, почта;
- [ ] территория выезда и текст доплаты;
- [ ] акцентный цвет — задаётся в кабинете; HEX валидируется, контраст с фоном и
      белым текстом проверяется на сервере, мягкие оттенки выводятся из одного цвета;
- [ ] тексты первого экрана (заголовок и подпись);
- [ ] режим «Другое»: требуется фото или нет.

Акцент подставляется в CSS-переменные на сервере, поэтому нет мигания цвета при загрузке.
Первый экран и метаданные обновляются без пересборки.

## 3. Услуги, цены и правила расчёта

Всё меняется в кабинете → «Услуги и цены», без правки кода:

- [ ] созданы категории, услуги и варианты под нишу клиента;
- [ ] у каждого варианта заданы единица (`шт`, `м²`, `м.п.`), подпись параметра,
      цена за единицу, min/max/step;
- [ ] опции `percent`, `fixed` и `fixed_order` заведены и привязаны к нужным вариантам;
- [ ] минимум заказа относится к работам, выезд — отдельно;
- [ ] порядок процентов и округления совпадает с согласованным;
- [ ] проверено кнопкой «Проверить расчёт» и на реальной заявке:
  - [ ] одна позиция;
  - [ ] количество/площадь больше значения по умолчанию;
  - [ ] процентная опция;
  - [ ] фикс за штуку со своим количеством;
  - [ ] фикс за заказ;
  - [ ] срабатывание минимума;
  - [ ] выезд за город;
  - [ ] смешанный заказ с «По фото».

Нестандартная формула (цена от двух параметров, условия, ступенчатые скидки)
по-прежнему меняется **в одном месте**: `src/lib/calc/pricing.ts`.
Тесты: `src/lib/calc/pricing.test.ts`.
Порядок применения зафиксирован: значение параметра × цена за единицу → опции
строки → сумма → минимум → фикс заказа → выезд → округление. Проценты
применяются последовательно.

Снимок каталога и расчёта хранится в каждой заявке. Изменение прайса не трогает
старые заявки. Уже отправленные заявки можно пересчитать только вручную — это
осознанное ограничение.

## 4. Бренд и оформление

Меняется в кабинете: название, контакты, тексты, акцент.
Требует исходников: логотип, полная палитра, PWA-иконки, шрифты, новые разделы и
нестандартная формула. Обычные новые услуги настраиваются в кабинете.

- [ ] Логотип в шапке и в иконках PWA (192, 512, maskable). Сейчас иконки
      сгенерированы из глифа-заглушки: `public/icons/*`, `src/app/icon.svg`,
      `scripts/generate-assets.ts`. **Требует исходников клиента.**
- [ ] `manifest`: название, короткое имя, цвета, `standalone` — генерируется из БД
      (`src/app/manifest.ts`), менять вручную не нужно.
- [ ] Метаданные и OG-картинка (`public/og.png`, `app/layout.tsx`). OG тоже
      сгенерирована из заглушки — заменить на брендовую.
- [ ] Проверить, что тёмная тема не «съедает» логотип.
- [ ] Шрифт Onest — SIL OFL, лежит в сборке Next; замена гарнитуры требует исходников.

## 5. Проверка перед передачей

- [ ] Клиентский путь целиком: выбор → корзина → фото и контакты → заявка →
      приватная ссылка.
- [ ] Владелец вошёл, увидел заявку, поставил цену и время, сменил статус.
- [ ] Клиент увидел обновление по своей ссылке (опрос раз в 20 секунд при видимой
      вкладке + кнопка «Обновить»).
- [ ] Повторная отправка не создала дубль (idempotency key, 24 часа).
- [ ] Чужая заявка по прямому URL не открывается (404).
- [ ] Фото не открывается по прямому адресу без права (404).
- [ ] Мобильная ширина 360 px, светлая и тёмная темы.
- [ ] Цены на сайте совпадают с прайсом клиента до рубля.
- [ ] Блок «Наши работы»: фото загружены, порядок и скрытие проверены, пустое
      состояние не показывает секцию. Пары «до/после» листаются и перетаскиваются.

Автоматически:

```bash
npm run typecheck
npm run lint
npm run test
npm run test:e2e
npm run build
```

`npm run test:e2e` проверяет основной сценарий и вёрстку 360/390/1280.

## Объём адаптации (базовый пакет)

Входит: конфиг компании, настройка категорий/услуг/вариантов/параметров и опций в
кабинете, тексты, акцент, иконки PWA, настройка домена и сервера, проверка расчёта,

скидки), онлайн-оплата, расписание мастеров, роли и права, CRM, SMS/почтовые
уведомления, интеграции, разработка новых экранов, смена логотипа дизайнером,
полная смена палитры и гарнитуры.

Всё, что вне пакета, оценивается отдельно — до начала работ.

## Технические заметки для переноса

- Локально база может быть `pglite://.data/dev`; у клиента — обычный PostgreSQL.
  Диалект и миграции одинаковые.
- На Vercel фото обязаны жить в приватном S3/R2 (`PHOTO_STORAGE=s3`), локальный диск
  там не сохраняется. На VPS — `local` и том `uploads`.
- `AUTH_SECRET` обязателен в продакшене: без него приложение не стартует (в dev есть
  запасное значение).
- Миграции на VPS применяются при старте контейнера (`RUN_MIGRATIONS=1`), на Vercel —
  вручную из локальной машины с прод-`DATABASE_URL`.
- PWA иконки и OG — единственные ассеты, которые нельзя получить из БД; их замена
  требует исходников.
